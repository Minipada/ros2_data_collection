    1. Usability

         1.1. Can load configuration from YAML UID: MS-USAB-001 statement:

    All configuration can be passed as a standard ROS 2 YAML configuration file.

    2. Plugin Loading

         2.1. Can load any number of measurement plugins UID: MS-PLU-001 statement:

    The Measurement server must be able to load any number of measurement plugins that conform to a specific interface. The plugins should be loaded dynamically at runtime.

         2.2. Can handle errors when loading measurement plugins UID: MS-PLU-002 statement:

    If the Measurement server attempts to load a plugin that does not conform to the specified interface or the plugin file does not exist, it should throw a custom exception with a clear error message. The node should then stop processing.

         2.3. Can load any number of condition plugins UID: MS-PLU-003 statement:

    The Measurement server must be able to load any number of condition plugins that conform to a specific interface. The plugins should be loaded dynamically at runtime.

         2.4. Can handle errors when loading condition plugins UID: MS-PLU-004 statement:

    If the Measurement server attempts to load a plugin that does not conform to the specified interface or the plugin file does not exist, it should throw a custom exception with a clear error message. The node should then stop processing.

         2.5. Extensibility and customizability UID: MS-PLU-005 statement:

    The system should be easily extensible and customizable, allowing users to add new features, plugins, and functionality to meet their specific requirements in the repository.

         2.6. External extensibility and customizability UID: MS-PLU-006 statement:

    The system should be easily extensible and customizable, allowing users to add new features, plugins, and functionality to meet their specific requirements in their own ROS packages.

         2.7. Can reload plugins without restarting the node UID: MS-PLU-007 statement:

    The Measurement server should be able to reload plugins dynamically without having to stop and restart the node. This will allow for updates and changes to be made to the plugins without interrupting data processing.

         2.8. Can unload plugins UID: MS-PLU-008 statement:

    The Measurement server should be able to unload plugins dynamically. This will allow for plugins to be removed from the system when they are no longer needed.

         2.9. Can provide information about loaded plugins UID: MS-PLU-08 statement:

    The Measurement server should be able to provide information about the plugins that are currently loaded, such as their names, version numbers, description and json schema.

    3. Collect

         3.1. Polling intervals UID: MS-COL-001 statement:

    The system should allow for different polling intervals for different measurements

         3.2. Dynamic polling intervals UID: MS-COL-002 statement:

    The system should allow for changing the polling interval during runtime.

         3.3. Real-time data processing UID: MS-COL-003 statement:

    The system should be able to process data in real-time, with minimal latency, to support time-critical applications.

         3.4. Concurrent data retrieval by plugins UID: MS-COL-004 statement:

    Multiple plugins should be able to fetch data in parallel without blocking or delaying each other, in order to ensure efficient and responsive data collection.

         3.5. Can enable/disable sample buffering UID: MS-COL-005 statement:

    The user can enable or disable the buffering of samples in case the remote destination is not available.

         3.6. Ability to set a maximum time to collect samples UID: MS-COL-006 statement:

    The system should provide an option to stop collecting samples after a certain amount of time has elapsed.

    4. File saving

         4.1. Can set local base path used by all nodes UID: MS-FIL-001 statement:

    The Measurement server must be able to load a local base path from a save_local_base_path parameter. This base path will be used by all nodes running in the server instance.

         4.2. Can expand time variables in the local base path UID: MS-FIL-002 statement:

    The Measurement server should support time variables in the save_local_base_path parameter, such as %Y, %m, and %d. These variables should expand to the current year, month, and day, respectively. If an unknown variable is encountered, the node should stop processing.

         4.3. Can expand environment variables in the local base path UID: MS-FIL-003 statement:

    The Measurement server should support environment variables in the save_local_base_path parameter, denoted by a $ or ${} symbol. If an empty variable is encountered, the node should stop processing.

    5. Custom variables

         5.1. Can load custom variables UID: MS-VAR-001 statement:

    The custom_keys_str parameter should allow the user to specify custom variables. Each variable should have a name subparameter and either a value or value_fromfile subparameter. If a required subparameter is missing or the file specified in value_from_file does not exist, the node should stop processing.

         5.2. Can load custom variables from a file UID: MS-VAR-002 statement:

    The custom_keys_str parameter should allow the user to specify custom variables that are loaded from a file. If the file specified in value_from_file does not exist, the node should stop processing.

         5.3. Can load custom variables from a fixed string UID: MS-VAR-03 statement:

    The custom_keys_str parameter should allow the user to specify custom variables that are loaded from a fixed string. If the value subparameter is empty, the node should stop processing.

    6. Data aggregation

         6.1. Can handle data aggregation UID: MS-AGG-001 statement:

    The system should be able to aggregate data from multiple sources and provide a unified view of the data.

     comment:

    Measurement 1:

    {"a": 1}

    Measurement 2:

    {"b": 2}

    Aggregated sample:

    {"a": 1, "b": 2}
    6.2. Ability to aggregate samples based on tags UID: MS-AGG-002 statement:

    The system should allow for grouping of samples based on tags, such as aggregating data from multiple sources with the same tag into a single output or view.

    7. Validation

         7.1. Validation of data samples through JSON schema UID: MS-VAL-001 statement:

    The system must be able to validate each data sample using a JSON schema, following standard schema patterns.

     comment:

    The validation of JSON data must follow the validation standard outlined in version 7 of the JSON schema specification, available at https://json-schema.org/draft/2020-12/json-schema-validation.html. The system must be able to validate each data sample against the specified schema to ensure that the data conforms to the defined structure and data types.

         7.2. Ability to pass a custom JSON schema for validation UID: MS-VAL-002 statement:

    The system should be able to accept a custom JSON file for validation that follows the standard schema patterns.

         7.3. Error reporting for failed validation UID: MS-VAL-003 statement:

    The system should provide clear error messages when a data sample fails validation, including the specific validation rule that was not met.

    8. Filters

         8.1. Ability to filter a sample by keeping only certain key values before validation UID: MS-FILT-001 statement:

    The system should be able to apply a filter that keeps only certain key values from a sample before validation.

         8.2. Ability to exclude a field through a filter UID: MS-FILT-002 statement:

    The system should be able to apply a filter that excludes one or multiple keys from the sample.

         8.3. Ability to filter samples based on a regular expression pattern UID: MS-FILT-003 statement:

    The system should be able to filter samples based on a regular expression pattern for a specific key. The user should be able to specify the key and the regular expression pattern to match.

         8.4. Ability to chain multiple filters together UID: MS-FILT-004 statement:

    The system should be able to chain multiple filters together, allowing the user to apply multiple filters to a sample in a specific order. The order of the filters should be configurable.

    9. Matching

         9.1. Ability to match measurement samples to a specific destination using tags UID: MS-MAT-001 statement:

    The system should be able to match a sample to a specific destination using tags.

         9.2. Can send data to multiple destinations simultaneously UID: MS-MAT-002 statement:

    The measurement system can send data to multiple destinations simultaneously, allowing for redundancy, load balancing, or other purposes.

    10. Maximum collect

         10.1. Ability to collect a certain amount of samples when the node starts UID: MS-MAX-001 statement:

    The system should provide an option to stop collecting samples after a certain amount of samples has been reached.

         10.2. Ability to delete the publisher when the maximum amount of samples has been reached UID: MS-MAX-002 statement:

    The system should stop the publisher and the loop when the maximum amount of samples has been reached.

         10.3. Ability to delete the subscriber when the maximum amount of samples has been reached UID: MS-MAX-003 statement:

    The system should stop the subscriber and the loop when the maximum amount of samples has been reached.

         10.4. Ability to collect samples when the node starts UID: MS-MAX-004 statement:

    The system should provide an option to collect a sample when starting the node directly, instead of waiting for the timer to elapse.

         10.5. Can send a maximum number of samples when conditions are met UID: MS-MAX-005 statement:

    Sometimes, it is useful to send data when conditions are respected and only a certain amount of time

     comment:

    This requirement means that the system can specify a maximum number of data samples to be sent when certain conditions are met. This can be useful for cases where the system needs to limit the amount of data sent for performance or resource usage reasons.

    11. Metadata keys

         11.1. Ability to include measurement name in sample UID: MS-MET-001 statement:

    The system should provide the option to include the measurement name as a key/value pair in each sample.

         11.2. Can include measurement plugin name in sample UID: MS-MET-002 statement:

    Each sample can have (or not) the measurement plugin name included as key/value

     comment:

    This requirement means that each data sample collected by the system can include the name of the measurement plugin that collected it. This can be useful for keeping track of which plugin collected which data, and for debugging purposes.

         11.3. Add timestamp to sample UID: MS-MET-003 statement:

    Each sample has a timestamp included, as a UTC absolute time.

    12. Remote paths

         12.1. Can pass remote keys UID: MS-PAT-001 statement:

    Can precise the remote key, based on remote destination

     comment:

    This requirement means that the system can specify which remote key to use when sending data to a particular destination. This can be useful for cases where the remote system requires a specific key to be used, or for cases where multiple keys are valid but only one should be used.

         12.2. Can apply a prefix to the remote key UID: MS-PAT-002 statement:

    Can pass a prefix to the remote key, to add a string to the path

     comment:

    This requirement means that the system can add a prefix to the remote key when sending data to a particular destination. This can be useful for cases where the remote system requires a specific path to be used, or for cases where the system needs to differentiate between different paths for the same destination.

    13. Conditions

         13.1. Can send samples if all conditions are respected (from a list of condition) UID: MS-CON-001 statement:

    Can pass a list of conditions. All need to be all respected to send data sample

     comment:

    This requirement means that the system can define a list of conditions that must all be true in order for a data sample to be sent. This can be useful for cases where certain criteria must be met before data can be sent, such as when the system needs to ensure that the data is of a certain quality or meets certain requirements.

         13.2. Can send samples if any conditions is respected (from a list of condition) UID: MS-CON-002 statement:

    Can pass a list of conditions. One of them need to be respected to send data sample

     comment:

    This requirement means that the system can define a list of conditions and send a data sample if any of them are true. This can be useful for cases where there are multiple criteria that can be met for data to be sent, and only one needs to be met for the data to be sent.

         13.3. Can send samples if no conditions are not respected (from a list of condition) UID: MS-CON-003 statement:

    Can pass a list of conditions. None need to be respected to send data sample

     comment:

    This requirement means that the system can define a list of conditions and send a data sample if none of them are true. This can be useful for cases where the system needs to ensure that data is not sent if certain criteria are met, such as if the data is of poor quality or does not meet certain requirements.

         13.4. Can access condition state from measurements UID: MS-CON-004 statement:

    Each measurement should be able to access through a variable the state of conditions it depends on.

    14. Lifecycle

         14.1. Stop all nodes if one fails UID: MS-LIF-001 statement:

    Include a bond connection for the lifecycle manager to ensure that after a server transitions up, it also remains active. If a server crashes, it lets the lifecycle manager know and transition down the system to prevent a critical failure.

    15. Compression

         15.1. Can compress samples before publishing UID: MS-COMP-001 statement:

    Samples can be large and compressing them before publishing can reduce network bandwidth usage and transmission time.

         15.2. Support for gzip compression UID: MS-COMP-002 statement:

    The system shall support gzip compression of JSON data. The compressed data must be compatible with the gzip compression standard.

         15.3. Support for deflate compression UID: MS-COMP-003 statement:

    The system shall support deflate compression of JSON data. The compressed data must be compatible with the deflate compression standard.

         15.4. Support for Brotli compression UID: MS-COMP-004 statement:

    The system shall support Brotli compression of JSON data. The compressed data must be compatible with the Brotli compression standard.

         15.5. Support for LZ77 compression UID: MS-COMP-005 statement:

    The system shall support LZ77 compression of JSON data. The compressed data must be compatible with the LZ77 compression standard.

         15.6. Support for LZ4 compression UID: MS-COMP-006 statement:

    The system shall support LZ4 compression of JSON data. The compressed data must be compatible with the LZ4 compression standard.

         15.7. Ability to choose compression algorithm UID: MS-COMP-007 statement:

    The system shall allow users to choose between different compression algorithms (such as gzip, deflate, Brotli, LZ77, LZ4, etc.) for compressing JSON data.

         15.8. Performance benchmarking UID: MS-COMP-008 statement:

    The system shall provide performance benchmarks for each compression algorithm to help users choose the most efficient algorithm for their needs.

         15.9. Configurable compression level UID: MS-COMP-009 statement:

    The system shall allow users to configure the level of compression for each algorithm. The compression level should affect the balance between compression ratio and compression speed.

         15.10. Compression compatibility with JSON schema UID: MS-COMP-010 statement:

    The compressed JSON data must be compatible with JSON schema and should be able to be decompressed without any loss of data or information.

         15.11. Compression and decompression efficiency UID: MS-COMP-011 statement:

    The system shall provide efficient compression and decompression algorithms that minimize CPU usage and memory consumption while achieving high compression ratios.

    16. Limitations

         16.1. Can limit bandwidth usage for remote connections UID: MS-LIM-001 statement:

    The system should be able to limit the amount of data sent over a remote connection in order to manage bandwidth usage.
