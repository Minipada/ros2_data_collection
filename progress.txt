### #244 - DC 2.0 S3: dc_bridge tracer bullet — Records flow to Vector console

- Added a new `dc_bridge` package (ADRs 0001/0004/0006): the first Rust package in the
  repo, `package.xml` build type `ament_cargo` (colcon's Rust/ros2_rust integration,
  distinct from `ament_cmake` used everywhere else).
- Split it into two crates so the ROS-independent logic is unit-testable without a ROS
  install:
  - `dc_bridge/dc_bridge_core/` — a standalone Cargo crate (declares `[workspace]` so it
    never gets pulled into the outer package's workspace) with **zero ROS dependencies**:
    - `forwarder.rs` — `Forwarder::send(record)` hides Fluent Forward msgpack framing
      (`rmpv`), socket lifecycle, lazy reconnection (drops the connection on any write
      error other than would-block/timeout, so the *next* `send()` reconnects), and
      backpressure (a write that blocks past `write_timeout` is reported as
      `ForwarderError::Backpressure` *without* dropping the connection, since the peer
      may just be slow to drain).
    - `supervisor.rs` — `Supervisor` spawns an arbitrary `Command` and `poll_restart()`s
      it back to life if it has exited, subject to a `restart_backoff` to avoid restart
      storms. Deliberately agnostic to what program it supervises so the tests exercise
      it without needing the real Vector binary.
    - `readiness.rs` — `Readiness` (shared atomic ready/not-ready state) plus a plain TCP
      connect `probe()` against Vector's Forward address (ADR-0006: the Bridge has no
      lifecycle state beyond "process up + ready service answers").
    - `config.rs` — `TopicConfig` derives a Fluent Forward tag from a ROS topic name
      (`/dc/measurement/uptime` → `dc.measurement.uptime`) unless one is given explicitly.
    - `vector_config.rs` — renders the minimal Vector config (Fluent Forward source →
      console sink) and locates the vendored binary by scanning `AMENT_PREFIX_PATH` for
      `lib/vector_vendor/vector` (the path `vector_vendor`'s CMakeLists.txt installs to).
  - `dc_bridge/src/main.rs` — the actual `rclrs` ROS node: declares `topics`,
    `vector_forward_host`, `vector_forward_port`, `vector_binary` parameters; starts the
    Supervisor against the vendored Vector binary; subscribes to each configured topic,
    converting `StringStamped` (`header.stamp` + `data` JSON + `group_key`) into a
    `Record` and forwarding it; exposes a `~/ready` (`std_srvs/Trigger`) readiness
    service backed by a background thread that polls both `Supervisor::poll_restart()`
    and the readiness probe.
- Wired `dc_bridge` into `dc_bringup`: added a `dc_bridge` params block to
  `dc_params.yaml`, and a plain `Node` action for it in both the composed and
  non-composed branches of `dc_bringup.launch.py` (rclrs has no `rclcpp_components`
  equivalent, so unlike `measurement_server` it's never a `ComposableNode` — consistent
  with ADR-0006, it's also not in `lifecycle_manager_dc`'s `node_names`). Replaces the
  `dc_destinations`-COLCON_IGNORE comment's "nothing launched here" note with a pointer
  at `dc_bridge` as its ADR-0001/0004/0006 replacement.
- **Verified without `colcon`/`rclrs`** (no ROS 2 or ros2_rust install in this sandbox,
  same constraint as #242/#243): ran `cargo test` for real inside
  `dc_bridge/dc_bridge_core/` — all 16 tests pass (5 runs in a row, no flakiness),
  covering every scriptable Forwarder/Supervisor/Readiness acceptance criterion:
  - Frame correctness (decodes the exact `[tag, [[time, record]]]` Forward Mode

### #244 follow-up — added a colcon-test-integrated integration test, found and fixed a real Vector-orphaning bug it caught

Prompted by "do we have any tests?" / "we always need integration tests for the
workflow": `dc_bridge_core`'s 16 tests cover the ROS-independent logic, but `dc_bridge`'s
actual ROS node (`src/main.rs`) had zero automated coverage — everything about it had
only ever been checked by hand, interactively, in the (now torn-down) Docker session.

- Confirmed `colcon test` for an `ament_cargo` package is just `cargo test` + `cargo fmt
  --check` (colcon-ros-cargo's `AmentCargoTestTask` wraps `colcon_cargo.task.cargo.test`
  — read its source directly rather than guessing), so a real Rust integration test in
  `dc_bridge/tests/end_to_end.rs` gets picked up by the standard `colcon test` pipeline
  with no new package or build-type wrinkle needed.
- Added `dc_bridge/tests/end_to_end.rs`, two tests:
  - `published_record_reaches_vectors_console_sink` — spawns the real `dc_bridge`
    binary, uses `rclrs` itself (a test-side node: a `std_srvs::srv::Trigger` client
    polling `/dc_bridge/ready`, a publisher on the configured topic) to wait for
    readiness then publish a Record, and asserts the JSON reaches Vector's console sink
    via the child process's captured stdout. Automates the manual demo from the
    original #244 verification pass.
  - `stops_the_supervised_vector_process_on_sigterm` — sends SIGTERM to `dc_bridge` and
    asserts its supervised Vector process (identified precisely as `dc_bridge`'s direct
    child via `pgrep -P`, not by matching the Vector binary path system-wide, which
    proved flaky once leftover Vector processes from earlier debugging accumulated in
    the long-lived verification container) actually stops.
- The second test caught a real, undocumented bug: `rclrs::Context::ok()`
  unconditionally returns `true` today (confirmed by reading `rclrs/src/context.rs` —
  no signal handler exists yet), so `executor.spin()` in `main.rs` never returned on
  its own. Combined with the Supervisor living inside a `std::thread::spawn`'d closure
  that loops forever (never dropped through any normal control flow), this meant
  **Vector was orphaned on every shutdown** — Ctrl-C, `ros2 launch` stopping the node,
  or a plain `kill <pid>` — not just an unavoidable SIGKILL. Fixed by wrapping the
  Supervisor in `Arc<Mutex<_>>` and installing an explicit `ctrlc::set_handler` (the
  `termination` feature is required for SIGTERM/SIGHUP, not just SIGINT — missing it
  was itself a dead end diagnosed and fixed along the way) that stops Vector and exits
  before the process would otherwise just die via the OS default.
- Iterated against the real Docker environment throughout (writing rclrs-API-correct
  Rust from the cloned ros2_rust/rclrs source rather than guessing, same discipline as
  the original #244 pass): fixed a type-inference gap in the service-client call, ran
  `cargo fmt` to satisfy colcon's bundled format check, and diagnosed a genuinely flaky
  first version of the SIGTERM test down to its root cause (broad `pgrep -f` matching
  ANY Vector process on the machine, not the one this specific test spawned) rather
  than accepting the flakiness or loosening the assertion.
- `colcon test --packages-select dc_bridge` now passes 2/2 reliably (run 8+ times in a
  row, including deliberately in a container already contaminated with leftover/zombie
  processes from earlier debugging, to prove the fix was real and not environment luck).
- `dc_bridge/README.md` and the `main.rs` module doc comment updated to describe the
  test file, the three real bugs found in this environment (adding the Vector-orphaning
  one to the two from the original pass), and the shutdown behavior.

### #245 - DC 2.0 S4: Config renderer + PostgreSQL blessed destination

- Added `dc_bridge_core::render` (`dc_bridge/dc_bridge_core/src/render.rs`, new module):
  a pure, I/O-free config renderer (ADR-0003) mapping the unified `shipper`/
  `destinations` ROS parameter contract to a complete Vector TOML config — a `fluent`
  source; one `remap` (VRL) transform that normalizes each blessed destination's
  timestamp into its `time_key` per `time_format` (`double` = Unix epoch seconds as an
  f64, `iso8601` = `%Y-%m-%dT%H:%M:%S%.9f`), replacing the Humble-era chained Lua filters
  (`dc_destinations/include/dc_destinations/flb_destination.hpp` on `humble`); one
  `route` transform literally named `dc`, so Vector's own `<transform_id>.<route_id>`
  addressing convention gives every Destination a stable `dc.<name>` output for free
  (ADR-0003's passthrough contract) — verified this addressing scheme, and the VRL
  itself, against the real vendored Vector 0.57.0 binary (`vector vrl`, `vector validate
  --no-environment`) before writing any Rust; a disk buffer (`shipper.data_dir`,
  Vector's own documented ~256 MiB `postgres`-sink minimum, `MIN_DISK_BUFFER_BYTES`); and
  a `postgres`-type sink per destination (`postgres://user:pass@host:port/db`, with
  byte-wise percent-encoding of user/password so arbitrary credential characters can't
  corrupt the URI). Only `postgres` is implemented; `s3`/`file`/`console` are reserved
  blessed-type names that reject clearly (`RenderError::UnsupportedType`) until their
  own issues land.
- Two pure, independently-testable layers: `destination_from_raw`/
  `PostgresParams::from_raw` validate the flat, stringly-typed values ROS parameters
  naturally give (`<name>.type`, `<name>.host`, …) into typed config — this is where
  every "invalid-parameter rejection" acceptance criterion (unknown `type`, bad
  `time_format`/`receives`, missing required field, out-of-range port, empty
  `inputs`/`destinations`, duplicate/invalid destination names, an undersized disk
  buffer) becomes a `RenderError` variant with its own test; `render` turns an
  already-validated `RenderConfig` into the Vector TOML text. `expand_env` implements
  the `$NAME`/`${NAME}` expansion `shipper.data_dir` and each destination's `password`
  use, via an injected lookup closure rather than reading the real environment, so it
  stays pure/deterministic under test.

### #247 - DC 2.0 S6: Launch integration — deterministic startup ordering

`.github/workflows/ci.yaml` itself was **replaced outright**, not left alongside a new

(`COLCON_IGNORE`d per ADR-0001/#242) so the old Docker/`industrial_ci` workflow was
already unreachable dead weight on this branch; deleting it doesn't touch `humble`'s

Three real architecture course-corrections happened mid-session, each prompted by
direct pushback rather than found independently — recorded here because the *reasons*
matter for whoever touches this next:

- **One shared build, not a CI-only script.** The first pass split a toolchain-only
  `ci/jazzy/Containerfile` from a bespoke `ci/jazzy/run_ci.sh` script that did the
  actual `rosdep install`/`colcon build`/`colcon test` at container-*run* time,
  separate from `tools/e2e/Containerfile`'s own full-workspace `RUN colcon build` —
  duplicate build logic for no real gain, since the only reason for the split (avoid
  rebuilding a multi-minute image every CI run) is solvable properly with a registry-
  backed build cache instead (next point). `ci/jazzy/` no longer exists; there is one
  `tools/e2e/Containerfile` (two stages: `toolchain` — ROS jazzy-ros-base +
  Rust/rustup + `colcon-cargo`/`colcon-ros-cargo` + `libclang-dev` + `fastcov`/`lcov` —
  then `workspace`, `FROM toolchain`, the actual build), and `tools/e2e/scripts/
  build.sh`/`test.sh` are the *same* scripts a developer runs locally that CI also
  calls directly — no CI-only script anywhere.
- **Registry-backed build cache, verified before relying on it.** Podman's own
  `--layers` cache is local-only and doesn't survive a GitHub-hosted runner (a fresh VM
  every job). Confirmed `podman build --cache-from`/`--cache-to` against a registry
  actually solves this (podman 5.4.2, not just from `--help` text) via a throwaway
  local `registry:2` container: built with `--cache-to`, deleted the local image *and*
  every layer (`podman rmi` + `podman image prune`), rebuilt with `--cache-from`
  only — podman pulled the cache blobs from the registry and reused them on an
  otherwise cold machine state. Wired to `ghcr.io/<repo>/dc-workspace-cache` in CI
  (authenticated via the built-in `GITHUB_TOKEN`, no new secrets — same registry
  `docker.yaml` already pushes humble images to). `build.sh`'s `CACHE_REF` env var is
  optional and unset for a plain local build.
- **Two Containerfiles after all — but layered, not duplicated.** Challenged again:
  why bake the harness's synthetic-workload files into the *same* image CI uses for
  `colcon test`, when CI never touches them? Split into **`tools/e2e/Containerfile`**
  (the shared workspace build above — what CI builds and tests directly) and
  **`tools/e2e/Containerfile.e2e`** (`ARG BASE_IMAGE` / `FROM ${BASE_IMAGE}`, just the
  workload generator/params/entrypoint — never built by CI). This is a genuinely
  different pattern from the `ci/jazzy/run_ci.sh` mistake above: a thin derived image
  `FROM`ing a shared base is exactly what `docker/ci-testing/Dockerfile` FROMing
  `docker/ci/Dockerfile` already does in this repo, not duplicate build logic. Bonus:
  `Containerfile.e2e`'s build context is `tools/e2e/` itself (3 small files), not the

- **rosdep resolves every key across every package *before* installing anything** — one
  unresolvable key aborts the *whole* install with zero system packages installed, not
  just that one package. A first attempt (`rosdep install ... || true`) masked this

  error. Fixed with `--skip-keys "rclrs rosidl_runtime_rs"` (genuinely rosdep-key-less

  needed a plain `apt-get update` before rosdep's install step in the `workspace`
  stage — the `toolchain` stage's own apt layer ends with `rm -rf
  /var/lib/apt/lists/*` to keep it small, so the index has to be refreshed downstream.

  https://sh.rustup.rs | sh` had no integrity check. Matches the discipline

  `tools/e2e/README.md`):
  - Discovered along the way that this repo's `.dockerignore` is an "ignore

### Bridge reverted from Rust to C++ (ADR-0007 supersedes ADR-0004)

Prompted by review during #249: the rclrs/ros2_rust pilot (ADR-0004, PRs #260-264)
could not deliver plug-and-play on Jazzy today — no stable rosidl_generator_rs (source-
built message repos + a git-pinned code generator), incomplete colcon-ros-cargo link-flag
generation (the whole example_interfaces/sibling-package COLCON_IGNORE saga above was a
symptom), and a Rust toolchain in every CI/dev image. None of the Bridge's actual work
needs Rust. Exercised ADR-0004's own exit clause ("if not, the loss is one small
package") and rewrote dc_bridge in C++. ADR-0007 records the decision and rationale.

- **dc_bridge is now `ament_cmake` C++ (`rclcpp`).** Faithful port of every Rust module,
  as clean classes:
  - Core (ROS-independent, gtest'd without ROS, buildable via a standalone
    `dc_bridge/test/local/` CMake for fast iteration): `forwarder` (msgpack-cxx framing +
    socket lifecycle/reconnect/backpressure), `supervisor` (fork/exec/waitpid +
    PR_SET_PDEATHSIG), `readiness`, `topic_config`, `render` (the 1500-line ADR-0003
    config renderer, toml++, gold-file tests reuse the old Rust fixtures byte-for-byte),
    `vector_binary`, and the whole `uploader/` (group/content_type/status/multipart/
    uploader) built on an abstract `ObjectStore` interface so it's tested against an
    in-memory fake with no cloud dep — the same split the Rust design had with
    object_store's InMemory.
  - Node (`bridge_node.cpp`/`main.cpp`): declares the shipper/destinations/files
    parameters, renders + `vector validate`s the config, spawns/supervises Vector,
    subscribes inputs, forwards Records, runs the Uploader worker thread, `~/ready`
    service. rclcpp handles SIGINT/SIGTERM + on_shutdown (no more manual ctrlc handler).
  - `uploader/s3_object_store.cpp`: the aws-sdk-cpp ObjectStore impl (the only piece
    linking the SDK).
- **New `aws_sdk_vendor` package**: builds aws-cpp-sdk-core+s3 from source (pinned tag
  1.11.600, `-DBUILD_ONLY=s3`, zlib compression off). Verified aws-sdk-cpp works fully
  with RustFS (PutObject + real multipart, both with and without the SDK's default
  request checksums) via a live smoke test *before* adopting it — the one real risk
  (newer AWS SDKs' default x-amz-checksum-crc32 header breaking S3-compat servers) is
  retired for RustFS. Builds in ~20 min; cached across CI runs.
- **The entire Rust toolchain leaves**: no rustup, colcon-cargo/colcon-ros-cargo,
  libclang, `ros2_data_collection_jazzy.repos` (deleted), or COLCON_IGNORE/--skip-keys
  Rust workarounds. `tools/e2e/Containerfile`, `ci.yaml`, and `test.sh` de-Rusted.
  dc_cli's stale dc_destinations exec_depend (a #242 leftover) removed.
- **Dependencies are all rosdep-resolvable**: rclcpp, dc_interfaces, std_msgs, std_srvs,
  nlohmann-json-dev, aws_sdk_vendor. The two header-only libs with no upstream rosdistro
  key (tomlplusplus, msgpack-cxx) resolve via a small repo-local rosdep source
  (`rosdep/dc.yaml`), registered by the Containerfile / documented for local dev in
  dc_bridge/README.md. A user now does `rosdep install && colcon build` like any dc_*
  package — the plug-and-play the Rust pilot couldn't deliver.
- **Verified in a real ROS 2 Jazzy container**: Phase 1 (records path) — colcon build
  --packages-up-to dc_bridge succeeds, 63 gtests pass. aws_sdk_vendor builds and installs
  a relocatable AWSSDKConfig.cmake + libaws-cpp-sdk-s3.so. The uploader core's 11 gtests
  (happy path, metadata shape, verify-retry, delete-after-verified-everywhere,
  no-dup-rows, missing-file, partial-vs-complete group, video duration, ffprobe parse,
  interrupted-multipart-resume, no-files-noop) pass against the in-memory fake.
- **Delivered in two commits**: Phase 1 (records path, `6c1c1c7`) then Phase 2
  (aws_sdk_vendor + Uploader).
- **Docs**: ADR-0007; dc_bridge/README.md rewritten for the C++ package; CLAUDE.md
  de-Rusted; doc/src/dc/logo_prompt.md added (new-logo AI prompts).
- **Not done / left for follow-up**: eliminating the one-line local rosdep registration
  (contribute tomlplusplus/msgpack-cxx keys upstream, or vendor the two headers); a
  prebuilt aws-sdk-cpp to avoid the ~20-min source build; GCS/Azure ObjectStore
  implementations (S3 only today, matching the Rust); the #268 gz-sim port
  (dc_demos/dc_simulation still COLCON_IGNORE'd, unrelated to the language change).
