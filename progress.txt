### #244 - DC 2.0 S3: dc_bridge tracer bullet — Records flow to Vector console

- Added a new `dc_bridge` package (ADRs 0001/0004/0006): the first Rust package in the
  repo, `package.xml` build type `ament_cargo` (colcon's Rust/ros2_rust integration,
  distinct from `ament_cmake` used everywhere else).
- Split it into two crates so the ROS-independent logic is unit-testable without a ROS
  install:
  - `dc_bridge/dc_bridge_core/` — a standalone Cargo crate (declares `[workspace]` so it
    never gets pulled into the outer package's workspace) with **zero ROS dependencies**:
    - `forwarder.rs` — `Forwarder::send(record)` hides Fluent Forward msgpack framing
      (`rmpv`), socket lifecycle, lazy reconnection (drops the connection on any write
      error other than would-block/timeout, so the *next* `send()` reconnects), and
      backpressure (a write that blocks past `write_timeout` is reported as
      `ForwarderError::Backpressure` *without* dropping the connection, since the peer
      may just be slow to drain).
    - `supervisor.rs` — `Supervisor` spawns an arbitrary `Command` and `poll_restart()`s
      it back to life if it has exited, subject to a `restart_backoff` to avoid restart
      storms. Deliberately agnostic to what program it supervises so the tests exercise
      it without needing the real Vector binary.
    - `readiness.rs` — `Readiness` (shared atomic ready/not-ready state) plus a plain TCP
      connect `probe()` against Vector's Forward address (ADR-0006: the Bridge has no
      lifecycle state beyond "process up + ready service answers").
    - `config.rs` — `TopicConfig` derives a Fluent Forward tag from a ROS topic name
      (`/dc/measurement/uptime` → `dc.measurement.uptime`) unless one is given explicitly.
    - `vector_config.rs` — renders the minimal Vector config (Fluent Forward source →
      console sink) and locates the vendored binary by scanning `AMENT_PREFIX_PATH` for
      `lib/vector_vendor/vector` (the path `vector_vendor`'s CMakeLists.txt installs to).
  - `dc_bridge/src/main.rs` — the actual `rclrs` ROS node: declares `topics`,
    `vector_forward_host`, `vector_forward_port`, `vector_binary` parameters; starts the
    Supervisor against the vendored Vector binary; subscribes to each configured topic,
    converting `StringStamped` (`header.stamp` + `data` JSON + `group_key`) into a
    `Record` and forwarding it; exposes a `~/ready` (`std_srvs/Trigger`) readiness
    service backed by a background thread that polls both `Supervisor::poll_restart()`
    and the readiness probe.
- Wired `dc_bridge` into `dc_bringup`: added a `dc_bridge` params block to
  `dc_params.yaml`, and a plain `Node` action for it in both the composed and
  non-composed branches of `dc_bringup.launch.py` (rclrs has no `rclcpp_components`
  equivalent, so unlike `measurement_server` it's never a `ComposableNode` — consistent
  with ADR-0006, it's also not in `lifecycle_manager_dc`'s `node_names`). Replaces the
  `dc_destinations`-COLCON_IGNORE comment's "nothing launched here" note with a pointer
  at `dc_bridge` as its ADR-0001/0004/0006 replacement.
- **Verified without `colcon`/`rclrs`** (no ROS 2 or ros2_rust install in this sandbox,
  same constraint as #242/#243): ran `cargo test` for real inside
  `dc_bridge/dc_bridge_core/` — all 16 tests pass (5 runs in a row, no flakiness),

  - Frame correctness (decodes the exact `[tag, [[time, record]]]` Forward Mode

### #244 follow-up — added a colcon-test-integrated integration test, found and fixed a real Vector-orphaning bug it caught

Prompted by "do we have any tests?" / "we always need integration tests for the
workflow": `dc_bridge_core`'s 16 tests cover the ROS-independent logic, but `dc_bridge`'s
actual ROS node (`src/main.rs`) had zero automated coverage — everything about it had
only ever been checked by hand, interactively, in the (now torn-down) Docker session.

- Confirmed `colcon test` for an `ament_cargo` package is just `cargo test` + `cargo fmt
  --check` (colcon-ros-cargo's `AmentCargoTestTask` wraps `colcon_cargo.task.cargo.test`
  — read its source directly rather than guessing), so a real Rust integration test in
  `dc_bridge/tests/end_to_end.rs` gets picked up by the standard `colcon test` pipeline
  with no new package or build-type wrinkle needed.
- Added `dc_bridge/tests/end_to_end.rs`, two tests:
  - `published_record_reaches_vectors_console_sink` — spawns the real `dc_bridge`
    binary, uses `rclrs` itself (a test-side node: a `std_srvs::srv::Trigger` client
    polling `/dc_bridge/ready`, a publisher on the configured topic) to wait for
    readiness then publish a Record, and asserts the JSON reaches Vector's console sink
    via the child process's captured stdout. Automates the manual demo from the
    original #244 verification pass.
  - `stops_the_supervised_vector_process_on_sigterm` — sends SIGTERM to `dc_bridge` and
    asserts its supervised Vector process (identified precisely as `dc_bridge`'s direct
    child via `pgrep -P`, not by matching the Vector binary path system-wide, which
    proved flaky once leftover Vector processes from earlier debugging accumulated in
    the long-lived verification container) actually stops.
- The second test caught a real, undocumented bug: `rclrs::Context::ok()`
  unconditionally returns `true` today (confirmed by reading `rclrs/src/context.rs` —
  no signal handler exists yet), so `executor.spin()` in `main.rs` never returned on
  its own. Combined with the Supervisor living inside a `std::thread::spawn`'d closure
  that loops forever (never dropped through any normal control flow), this meant
  **Vector was orphaned on every shutdown** — Ctrl-C, `ros2 launch` stopping the node,
  or a plain `kill <pid>` — not just an unavoidable SIGKILL. Fixed by wrapping the
  Supervisor in `Arc<Mutex<_>>` and installing an explicit `ctrlc::set_handler` (the
  `termination` feature is required for SIGTERM/SIGHUP, not just SIGINT — missing it
  was itself a dead end diagnosed and fixed along the way) that stops Vector and exits
  before the process would otherwise just die via the OS default.
- Iterated against the real Docker environment throughout (writing rclrs-API-correct
  Rust from the cloned ros2_rust/rclrs source rather than guessing, same discipline as
  the original #244 pass): fixed a type-inference gap in the service-client call, ran
  `cargo fmt` to satisfy colcon's bundled format check, and diagnosed a genuinely flaky
  first version of the SIGTERM test down to its root cause (broad `pgrep -f` matching
  ANY Vector process on the machine, not the one this specific test spawned) rather
  than accepting the flakiness or loosening the assertion.
- `colcon test --packages-select dc_bridge` now passes 2/2 reliably (run 8+ times in a
  row, including deliberately in a container already contaminated with leftover/zombie
  processes from earlier debugging, to prove the fix was real and not environment luck).
- `dc_bridge/README.md` and the `main.rs` module doc comment updated to describe the
  test file, the three real bugs found in this environment (adding the Vector-orphaning
  one to the two from the original pass), and the shutdown behavior.

### #245 - DC 2.0 S4: Config renderer + PostgreSQL blessed destination

- Added `dc_bridge_core::render` (`dc_bridge/dc_bridge_core/src/render.rs`, new module):
  a pure, I/O-free config renderer (ADR-0003) mapping the unified `shipper`/
  `destinations` ROS parameter contract to a complete Vector TOML config — a `fluent`
  source; one `remap` (VRL) transform that normalizes each blessed destination's
  timestamp into its `time_key` per `time_format` (`double` = Unix epoch seconds as an
  f64, `iso8601` = `%Y-%m-%dT%H:%M:%S%.9f`), replacing the Humble-era chained Lua filters
  (`dc_destinations/include/dc_destinations/flb_destination.hpp` on `humble`); one
  `route` transform literally named `dc`, so Vector's own `<transform_id>.<route_id>`

  (ADR-0003's passthrough contract) — verified this addressing scheme, and the VRL
  itself, against the real vendored Vector 0.57.0 binary (`vector vrl`, `vector validate
  --no-environment`) before writing any Rust; a disk buffer (`shipper.data_dir`,
  Vector's own documented ~256 MiB `postgres`-sink minimum, `MIN_DISK_BUFFER_BYTES`); and
  a `postgres`-type sink per destination (`postgres://user:pass@host:port/db`, with
  byte-wise percent-encoding of user/password so arbitrary credential characters can't
  corrupt the URI). Only `postgres` is implemented; `s3`/`file`/`console` are reserved
  blessed-type names that reject clearly (`RenderError::UnsupportedType`) until their
  own issues land.

  naturally give (`<name>.type`, `<name>.host`, …) into typed config — this is where

  `inputs`/`destinations`, duplicate/invalid destination names, an undersized disk
  buffer) becomes a `RenderError` variant with its own test; `render` turns an
  already-validated `RenderConfig` into the Vector TOML text. `expand_env` implements

### #246 - DC 2.0 S5: S3/file/console blessed destinations + passthrough contract

- Completed the blessed Destination set in `dc_bridge_core::render` (ADR-0003):
  `DestinationKind` now has `Postgres`, `S3`, `File`, and `Console` variants.
  - `s3` → Vector `aws_s3` sink: required `bucket`; optional `region`, `endpoint`
    (MinIO/Ceph-style custom endpoints), `key_prefix`, `access_key_id` +
    `secret_access_key` (validated as both-or-neither — half a pair is a clear
    `IncompleteS3Auth` startup error; omit both for ambient AWS credentials),
    `force_path_style`, and `batch_timeout_secs` (>0 validated; omitted, Vector's own
    300 s default applies). `secret_access_key` gets the same `$VAR` env expansion as
    the Postgres `password`. `encoding.codec = "json"` (Vector 0.57 removed the `ndjson`
    codec name; newline/array framing is the sink's default) + the shared disk buffer.
  - `file` → Vector `file` sink: required `path` (Vector template syntax passes
    through), JSON encoding, disk buffer.
  - `console` → Vector `console` sink on stdout, JSON encoding, deliberately *no* disk
    buffer (debugging sink; a disk buffer would replay old output across restarts).
  - `time_key`/`time_format` moved from `PostgresParams` up to `Destination` — they
    were always destination-generic (the Humble flb destinations all had them), and the
    normalize transform now renders one `if includes([tags], .tag)` block per
    destination of any type. `RawPostgresParams` became the flat, all-types
    `RawDestinationParams` (mirroring how ROS declares `<name>.*` params).
- **Aligned the passthrough routing contract with ADR-0003: routes are now per-Tag, not
  per-Destination.** #245 rendered one route branch per Destination (`dc.<name>`); the
  ADR and #246 fix the public name as `dc.<tag>` — one branch per distinct Tag across
  every Destination's `inputs`, branch id = the Tag verbatim, so Records for Tag
  `dc.measurement.uptime` are consumable at `dc.dc.measurement.uptime` (leading `dc.` =
  the route transform id, rest = Tag). Blessed sinks now consume their inputs' per-Tag
  routes (`sink_inputs`), and custom snippets consume exactly the same names. Verified
  against the real Vector 0.57.0 binary *before* writing the Rust (downloaded, checksum
  -verified against vector_vendor's pin): route ids containing dots validate and
  resolve, multi-`--config` merging works, and duplicate component ids across files are
  rejected by `vector validate` with a clear error.
- Passthrough (`custom_config_files` parameter): a list of raw Vector TOML snippet
  paths ($VAR-expanded), read at startup and validated by the new pure
  `validate_custom_config_files`: must parse as TOML, define ≥1 component, and not
  claim component ids owned by the rendered config (`dc_bridge_in`,
  `dc_bridge_normalize`, `dc` — destination names colliding with those are now also
  rejected via `ReservedDestinationName`, a latent #245 gap since a destination named
  `dc` would have collided with the route transform) or by another snippet — each its
  own `RenderError` variant with a test. Snippets are handed to Vector as extra
  `--config` args (`SupervisorConfig::vector` now takes a path list). As a backstop,
  `main.rs` runs `vector validate --no-environment` over the merged config set before
  the Supervisor starts (catches what pure checks can't: dangling `dc.<tag>` inputs,
  bad sink options), so every bad-snippet path is a loud startup error naming the file,
  never a supervised-Vector crash loop.
- Gold-file tests: 3 new fixtures (`s3_minio.toml` — custom endpoint + auth +
  force_path_style + batch timeout; `s3_aws.toml` — region + ambient credentials;
  `file_and_console.toml`) generated from the renderer's real output like #245's, and
  all 6 fixtures (3 regenerated for per-Tag routes) `vector validate`d against the real
  pinned binary. `dc_bridge_core` is now at 55 tests (`cargo test`, no ROS needed);
